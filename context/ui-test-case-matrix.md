# UI Test Case Matrix

_Generated by ui-test-design on 2026-09-23 (revised after a self-audit for positive/negative/edge coverage gaps), from `context/ui-context.md` and `context/ui-auth.md`. Re-run when either file changes._

**Rule IDs referenced below** (context files only state facts in prose/tables, not formal rule IDs — assigned here):

- RULE-1: Product cards (Home/Products) expose "Add to cart" (`a.add-to-cart[data-product-id]`) and "View Product"; an "Added!" confirmation modal element (`.close-modal`, "Continue Shopping") exists in the page's own DOM.
- RULE-2: `/products` provides a Search Product input (`#search_product`) + submit (`#submit_search`).
- RULE-3: `/products` sidebar links to `/category_products/{id}` and `/brand_products/{name}`.
- RULE-4: `/product_details/{id}` has a quantity input (`#quantity`), an Add-to-cart button, and a review form (`#name`/`#email`/`#review`/`#button-review`).
- RULE-5: `/view_cart` shows "Cart is empty! Click here to buy products." + a link to `/products` when empty (live-confirmed).
- RULE-6: `/login` email+password login (`data-qa="login-*"`); success redirects to `/` with "Logged in as {name}" + `a[href="/logout"]` visible (live-confirmed).
- RULE-7: `/login` shows "Your email or password is incorrect!" (red text, no id/data-qa) on invalid credentials (live-confirmed).
- RULE-8: `/login`'s signup mini-form (`data-qa="signup-*"`) navigates to `/signup`'s full account-details form (live-confirmed).
- RULE-9: `/signup`'s account-details form creates an account, redirects to `/account_created`, and auto-logs the user in on Continue (live-confirmed).
- RULE-10: Logout (`a[href="/logout"]`) ends the session, redirects to `/login` (live-confirmed).
- RULE-11: `Delete Account` link is visible only while logged in — confirmed present when logged in AND absent when logged out (both states directly observed).
- RULE-12: `/contact_us` has a Name/Email/Subject/Message/file-upload form (`data-qa` attributes) with Submit (live-confirmed fields; submission outcome not observed).
- RULE-13: Global nav is present on every page; `/test_cases` and `/api_list` confirmed to load; Video Tutorials links externally to YouTube (out of scope, per agreed scope).
- RULE-14: Checkout (address → payment → order confirmation) requires a non-empty cart + login; field-level structure not yet confirmed (`context/ui-context.md` Open Questions).
- RULE-15: Login/signup required fields are presumed mandatory (standard form pattern) but native `required`/validation attributes were not directly inspected.
- RULE-16 *(added on self-audit)*: `context/ui-auth.md`'s own Negative-auth-states table explicitly left "Session expired" unconfirmed — carried into this matrix as a designed case rather than left to silently drop.
- RULE-17 *(added on self-audit)*: Every form with an `email`-typed input (`login`, `signup`, product review, contact us) is assumed to reject a syntactically invalid email — not directly observed anywhere, and its total absence from the first draft of this matrix was the main gap this audit found.

Rows tagged **[Assumption]** go beyond what was directly observed — the underlying UI element's *existence* is sourced from `context/ui-context.md`/`context/ui-auth.md`, but the exact *behavior/outcome* wasn't live-confirmed during discovery. `ui-test-automation` is expected to re-verify these live before generating code from them — they are flagged design-time proposals, not fabricated facts.

## Open questions / follow-ups

- **RESOLVED before generation — Checkout's structure.** `ui-test-automation`'s Step 3 (re-verify stale assumptions live) drove the real flow end-to-end using the fixed test account: `/view_cart` → "Proceed To Checkout" → `/checkout` → "Place Order" → `/payment` → "Pay and Confirm Order" → `/payment_done/{id}`. All selectors in rows 38–40 are now live-confirmed, not assumed. Row 40 (invalid payment details) was later run live (2026-09-26) and found to be a real defect — see below.
- **RESOLVED before generation — a real assumption was found wrong.** The original matrix assumed the cart had an editable quantity field (rows 36–37 in the first draft). Live inspection found it's actually a **disabled `<button>`** — quantity can only be set on the product-details page. Row 36 was rewritten to test that non-interactivity directly instead of a feature that doesn't exist; row numbering shifted down by one for everything after Cart as a result. This is exactly the kind of stale-assumption catch `ui-test-automation`'s Step 3 exists for.
- **RESOLVED before generation — Contact Us has a native `confirm()` dialog** before submission that the original design didn't anticipate (row 43). Every contact-us test (rows 43–46) must accept this dialog or it will hang.
- **RESOLVED before generation — Account deletion** (row 42) is immediate on navigating `/delete_account`, with no confirmation step (unlike Contact Us, which does have one) — confirmed using a disposable throwaway account, `TEST_EMAIL` was never touched.
- **Test-account isolation for account deletion (row 42)** — still must use its own disposable account in generated code, never `TEST_EMAIL`, which every other authenticated test depends on.
- **Smoke-tag deviation for Account flow (row 41 vs. row 42)** — deliberately picked the non-destructive link-visibility check over the destructive deletion flow for the smoke tag, so smoke runs don't delete an account every execution. Flagging for explicit confirmation.
- **Self-audit additions (rows 4, 6, 8, 9, 16, 17, 21, 26, 30, 33)** — added after re-checking every flow against all 6 case types found real gaps: no flow had tested a malformed email format anywhere (rows 4, 16, 33, 45), `context/ui-auth.md`'s own flagged "session expired" state had never made it into a row (row 9), and there was no case at all for unauthenticated access to a login-gated page (row 8), non-numeric quantity input (row 30), or basic input-hygiene against a script-injection string (row 21). None of these are fabricated facts — same `[Assumption]` discipline as the rest of the matrix, just closing coverage gaps a first pass missed.
- **Remaining rows marked `[Assumption]`** (3, 10, 21, 25) are UI elements confirmed to exist, with exact behavior/outcome not live-verified. None were fabricated as facts; each is implemented defensively in code (asserting the safe invariant — e.g. "login did not succeed" — rather than a guessed exact error string) where the precise mechanism is unconfirmed.
- **Findings from the 2026-09-26 runs:**
  - **Five confirmed site defects**, each tracked as `xfail(strict=True)` so the suite stays green but XPASSes loudly if the site fixes them: row 11 (login email has no accessible label), row 17 (mobile number `123` accepted), row 26 (Enter doesn't submit product search), row 28 (quantity `0` accepted despite `min="1"`), row 40 (payment accepts a non-numeric card number). Rows 17 and 28 were hidden by tests that only asserted "the page didn't crash" — rewriting them to assert the real outcome exposed both.
  - **One authorization gap needing a human decision** — row 8: `/delete_account` has no route-level auth guard.
  - **Third-party ads are blocked** for every test (`src/core/browser_base.py`). Google's AdSense vignette interstitial randomly overlaid the page and swallowed clicks (root cause of row 22's flake, ~1 in 7 runs). Ads are outside the app under test.
  - **Every test runs in its own browser context** (superseding an earlier single-shared-window design, which leaked event listeners between tests and blocked parallel runs). Tests are order-independent and run in parallel with `pytest-xdist`.
  - **Tests clean up the accounts they create** (rows 13, 15, 17, 42) through the site's account API (`/api/deleteAccount`) in the `new_account` fixture's teardown — pass or fail. Row 42's throwaway account is also *created* through the API, since account creation isn't what that row verifies.
  - **Visibility checks now always wait.** Every positive `.is_visible()` (a one-shot check with no wait) was replaced with Playwright's web-first `expect(...).to_be_visible()`, which retries until the element appears or the timeout expires. Chromium happened to be fast enough to hide the race; Firefox exposed it in 9 tests.
  - **Cart → checkout waits for the page to load.** "Proceed To Checkout" is a jQuery click handler, not a link — clicking before the cart page's scripts run does nothing (confirmed on Firefox).
  - **Negative cases assert the real mechanism** — the browser's native constraint validation (`validationMessage`) for required/`type="email"` fields — instead of only "login did not succeed".
  - Full suite (58 tests): **53 passed, 5 xfailed** on each of Chromium, Firefox and WebKit (nightly CI run of 2026-09-29; on Firefox and WebKit, `test_checkout_happy_path` passed only on its automatic retry).
- **Browser/viewport matrix** — tied to the 3 browsers this project's `create-ui-framework-structure` run confirmed (Chromium, Firefox, WebKit; desktop viewport only). No mobile/tablet viewport was agreed, so no viewport-boundary cases were designed beyond that.
- **No PRD/Figma/Jira exist for this project** — every Rule cited above traces to `context/ui-context.md`/`context/ui-auth.md`'s own live-observed content.
- No exact-duplicate rows were found or removed during dedup; no `⚠ possible duplicate` rows either.
